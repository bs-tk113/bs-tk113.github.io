# 毎日の制作フロー

`/daily-post` で1記事分を回す。所要の目安は30〜60分（エージェント実行時間）。

```
[0] 灰島: 前回までの数字と学び（data/analytics.md, data/learnings.md）を3行に要約
      │
[1] 早瀬: キーワード候補×3 ──→ 灰島(データ根拠) + 日向(読者ニーズ) がレビュー
      │                         └→ 葛城が1つ選定（理由をログへ）
[2] 柚木: 構成案 ──→ 鳴海(SEO) + 日向(読者) ゲート  ※NGなら構成からやり直し
      │
[3] 柚木: 本文 ──→ 白石(事実) / 日向(読者) / 鳴海(SEO) 並列レビュー
      │            └→ 柚木は白石の指摘に1回だけ反論可
[4] 鳴海: タイトル案×3・メタ説明・slug・内部リンク ──→ 白石(誇大) + 日向(クリック欲)
      │
[5] 修正ループ（最大2回）── 収束しなければ葛城が裁定
      │
[6] 葛城: 公開判定 → docs/_posts/ に配置
      │
[7] 朝倉: SNS投稿文 ──→ 白石(炎上・誇大)チェック → promo/ に保存
      │
[8] 葛城: logs/ に制作ログを書く（テンプレ: logs/_template.md）
```

## ファイルの流れ

| 段階 | 置き場所 |
|------|----------|
| 作業中 | `drafts/<日付>-<slug>/`（keywords.md, outline.md, draft.md, reviews.md） |
| 公開記事 | `docs/_posts/<日付>-<slug>.md` |
| SNS文面 | `promo/<日付>-<slug>.md` |
| 制作ログ | `logs/<日付>-<slug>.md` |

## 週次（`/weekly-review`）

1. ユーザーが `data/analytics.md` にPV等を追記（Search Console / GA4 の数字を貼るだけでよい）。
2. 灰島が分析 → 「伸びた/伸びない理由の仮説」と「来週試すこと」を出す。早瀬と葛城がレビュー。
3. 学びを `data/learnings.md` に追記。全員が次回からこれを読む。
4. 各メンバーが**自分のエージェントファイルへの改善案**を1つ出し、葛城が採否を決めて反映（ルールの自己改善）。
5. 伸びた記事のリライト・内部リンク追加の候補を出す（既存記事の育成もPV施策）。

## 公開（push）について

`system/config.md` の `auto_publish` が `true` のときだけ git commit & push まで行う。
`false`（初期値）なら記事ファイルを置いて止まり、ユーザーが確認して公開する。
