## 導入（結論を先に。3行）
- 結論1: サブエージェントは `.claude/agents/` に Markdown を1枚置けば作れる。必須は `name` と `description` の2つだけ。
- 結論2: 呼ばれるかどうかは description でほぼ決まる。「何をする役か」より「いつ使うか」を具体的に書く。確実に呼びたい時は名前で指名する。
- 結論3: 後半では、このブログを実際に作っている「AI編集部」7体の定義と、うまくいかなかったことを見せる。

  - H3 何がうれしいのか：メインの会話を散らかさずに、調べ物やレビューを任せられる（独自のコンテキストで動き、要約だけ返す）

## H2-2 最小の1体を作る：ファイル1枚、必須項目は2つ
  - H3 置き場所は2つ：プロジェクト用 `.claude/agents/` と、全プロジェクト共通 `~/.claude/agents/`（表で比較。優先順位も1行）
  - H3 最小の定義ファイル（コピーして使える例を1つ。公式の例の翻訳ではなく、この記事用に書いたもの）
  - H3 `tools` と `model` は省略してよい：省略すると、ツールはメインから引き継ぎ、モデルは決められた順で選ばれる。「読むだけの役」は `tools` を絞るのがおすすめ
  - H3 作り方は2通り：Claude に頼む／自分でファイルを書く。`/agents` は版によって動きが違う（v2.1.197 以前はウィザード、今は案内メッセージ）ことを注意書きで
  - H3 動かしてみる：「〇〇 subagent を使って…」と頼み、トランスクリプトに `名前(タスク)` の行が出れば成功

## H2-3 ちゃんと呼ばれる description の書き方（副KW: description 書き方）
  - H3 Claude は description を見て「任せるか」を決めている（公式の記述を根拠に1〜2文）
  - H3 書き方の型3つ：(1) いつ使うか（きっかけ）を書く (2) 他のサブエージェントと役割がかぶらない言葉にする (3) 自動で任せてほしいなら「use proactively」のような一言を入れる
  - H3 悪い例 → 良い例（比較表。悪い例は「コードをレビューする」のような広すぎる1行。具体例はこの記事用に作るもので、体験談として書かない）
  - H3 長く書きすぎない：詳しい指示は本文（システムプロンプト）側へ。全体の description が 15,000 トークンを超えると起動時に警告
  - 分量の目安: 800字

## H2-4 サブエージェントが呼ばれないときのチェックリスト（副KW: 呼ばれない）
  - H3 そもそも読み込まれていない：`name` がない／`---` が1行目にない／`name` に `:` がある／`description` がない／YAML が壊れている → 黙ってスキップされる（表で）
  - H3 新しく `agents` フォルダを作った直後は再起動が要る（それ以外の追加・編集は再起動なしで数秒で反映）
  - H3 同じ名前が2つある：優先順位の高い方、または近い方が使われる。`/doctor` で同じフォルダ内の重複を見つけられる
  - H3 読み込まれているのに選ばれない：description が曖昧 → H2-3 の型で直す。それでもだめなら名前で指名する、`@` メンションで確実に呼ぶ
  - H3 原因を見る道具：`claude --debug` のデバッグログ、`claude plugin validate`（版の条件あり）
  - 分量の目安: 800字。スマホで見やすいよう「症状 → 原因 → 直し方」の3列表を1つ

## H2-5 応用・実例：このブログを作っている「AI編集部」7体の中身
  - H3 編集部の構成：リサーチ・執筆・SEO・校閲・読者代弁・拡散・分析の7体と、メインセッションが演じる編集長（system/team.md の表を簡略化）
  - H3 定義ファイルの抜粋：日向（読者代弁者）の frontmatter。`tools: Read, Glob, Grep` だけにして「ファイルを書き換えない」役にしている例。全文は GitHub リンク（URL は編集長が確認して記入）
  - H3 description に「どの手順で使うか」を書いている：7体とも description 末尾が「/daily-post のステップ〇で使う」。さらに手順書（SKILL.md）が名前で呼ぶので、自動の判断任せにしていない。H2-4 の「名前で指名する」の実例
  - H3 役割を分けると「指摘のやりとり」が生まれる：この記事のテーマ選定で、灰島は A（hooks 通知）を1位、日向は C（この記事）を1位にして推しが割れた。日向の「前半は最小の1体」という指摘がこの構成になり、灰島の「主KWを狭める」は一部だけ採用された（keywords.md・reviews.md の記録どおり）
  - H3 人が最後に決めていること：ブログのテーマはユーザーが選んだ。校閲（白石）の RED は編集長でも覆さないルール。auto_publish が false の間は公開・SNS投稿をしない
  - 分量の目安: 1,000字。抜粋は短く（数行）

## H2-6 うまくいかなかったこと：仕様の前提が、いつの間にか古くなっていた
  - 失敗例（記録にある事実だけ）: 編集部のルール（system/team.md）には「サブエージェントはサブエージェントを呼べないため、編集長だけはメインセッションが演じる」と書いてある。しかしこの記事のために 2026-10-22 に公式（ja/en）を確認したら、今はサブエージェントが自分のサブエージェントを生成できる（既定でメインの会話から3階層まで）と書かれていた

    - 書かないこと: 「いつの版で設計したか」「当時は正しかった」とは断定しない（記録がない）
  - 編集長をメインセッションに置く理由は今も別にある、と書けるか → 公式では、サブエージェントには AskUserQuestion（ユーザーに質問する道具）が渡されない。テーマ選びのようにユーザーに聞く役はメインに置く方が自然。ただしこれは「今の設計の理由づけ」であり、当初の理由として書かない

  - 分量の目安: 500字
